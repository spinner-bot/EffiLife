# 1327-T：正式发布签名门禁

## 元信息

- 日期：2026-10-12
- 类型：发布安全 / GitHub Actions
- 状态：已完成
- 关联：Windows NSIS、启动器签名诊断、内部 unsigned 产物

## 问题

启动器已经将 unsigned 安装包定义为内部验证产物，但 desktop tagged workflow 原先仍会在构建后无条件创建公开 GitHub Release，发布边界与诊断结论不一致。

## 实施内容

1. Windows runner 增加正式签名步骤，仅在 repository variable `EFFILIFE_FORMAL_RELEASE_ENABLED=true` 时启用。
2. 正式签名从 GitHub Secrets 读取 base64 编码的 PFX 和密码，不将证书写入仓库或日志。
3. 使用 `signtool.exe` 对 NSIS 安装包签名，并立即执行 `signtool verify /pa`；证书缺失、工具缺失、签名失败或验证失败都会使正式构建失败。
4. checksums 和 manifest 在签名完成后生成，确保摘要对应最终发布文件。
5. 公开 GitHub Release 同样要求显式正式发布变量；变量未开启时，构建仍生成内部验收 artifacts，但不会公开发布。
6. 增加 release workflow 契约测试和发布配置预检。

## 验证与边界

- 当前仓库未开启正式发布变量，也未配置正式证书；因此不会伪造或触发正式签名。
- 本机 Windows NSIS 和 Android unsigned 构建继续用于内部验收。
- Android release keystore、Linux/macOS 发行签名和 iOS 仍属于后续受控发布环境工作，不在本轮虚构为已完成。
