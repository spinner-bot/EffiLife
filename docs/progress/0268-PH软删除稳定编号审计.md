# 0670：PH 软删除稳定编号审计

## 审计问题

删除 PH 任务后，显示编号会压缩。例如删除 A2 后，原 A3 显示为 A2。需要确认统一工作区中的 TD 关联和历史日志是否会因此指向错误任务。

## 底层证据

- `plan-helper/modules/api.py::_active_task_entries` 保留原始有序槽位，只动态计算 `display_index`。
- `_task_id_for_display` 优先把仍然有效的内部槽位解析为 stable internal ID；显示编号仅作为删除槽位后的兼容解析方式。
- `get_tasks` 同时返回 `internal_id`、`display_id` 和 `internal_index`。
- PH 删除测试明确验证：删除 A2 后，活动任务显示为 A1/A2，但内部 ID 仍为 A1/A3。
- PH 历史 log 继续保存 A3；后续通过显示 A2 操作时，服务会解析回内部 A3。
- EffiLife 创建 TD 关联时使用 `task.internal_id`，并在展示/导航时同时兼容 internal/display 两类 ID。

## 结论

当前实现已经采用“存储 ID 稳定、显示 ID 动态压缩”的等价方案。不能在 TD 层把关联值改写为新的显示编号，否则会破坏删除后的历史定位和嵌套分组数据语义。

本次不修改代码，避免把一个已正确解决的底层问题改坏。后续若处理真正的硬删除，必须继续以 internal ID 和历史 log 引用为核心设计迁移策略。
