# EffiLife 进展报告规范

版本：1.0  
生效日期：2026-09-30

## 1. 目的与适用范围

`docs/progress/` 是 EffiLife 的持续进展、设计决策和验收证据目录。凡涉及统一应用壳、time-helper（TH）、plan-helper（PH）、to-dos（TD）、统一数据、主题、多语言、启动器、桌面/移动发布的工作，都必须在这里留下可追溯记录。

仓库中的 `docs/进展报告/` 保留为历史阶段资料；新工作、引用和 README 入口统一使用本目录，避免形成两套并行记录体系。

本目录记录事实和决策，不替代 `docs/spec/` 中的稳定规范，也不替代 `docs/HOTL/` 中的阶段验收要求。

## 2. 文件命名与编号

- `0000-进展报告规范.md` 是本目录的规范入口，不能用普通任务编号覆盖。
- 后续文件使用六位递增编号：`NNNN-简短主题.md`；编号不得复用。
- 设计和实现可以拆成两份记录，推荐分别使用“设计”和“实现”后缀；小型修复可使用一份完整记录。
- 文件名使用中文或清晰的英文领域名，避免只写模糊词（如“优化”“调整”）。

## 3. 每份报告的最低内容

每份报告至少包含：

1. 标题；
2. 日期；
3. 背景或发现的问题；
4. 目标与非目标；
5. 影响范围（模块、数据、平台）；
6. 实施内容或设计决策；
7. 兼容性与迁移说明；
8. 验证命令及结果；
9. 提交哈希与推送状态；
10. 未验证项、已知边界和后续事项。

如果是设计报告，必须明确“实现前提”和验收条件；如果是实现报告，必须回填实际命令和实际结果，不得用“计划执行”冒充完成证据。

## 4. 设计与实现流程

涉及前端界面时，先遵守 `docs/spec/UI 设计理念.md` 与 `docs/spec/UX 设计理念.md`，在报告中写明布局意图、桌面/移动差异、状态覆盖和主题变量策略，再修改代码。

涉及 PH 数据时，必须保持完整 Plan（head/main/log）、大写 section 索引、任务显示编号、嵌套 group 和软删除语义；内部实现可以等价调整，但不得改变逻辑结构或跨模块关联含义。

涉及统一存档时，必须说明 `effilife.bundle` 的 canonical datasets、校验/回滚策略和旧存档兼容性。涉及跨模块关联时，必须验证 PH、TD、TH 的独立职责没有被混为同一种实体。

## 5. 测试与证据等级

报告应区分以下状态：

- **已验证**：有实际命令输出、测试结果或可复现运行证据；
- **配置已验证**：静态门禁或契约测试通过，但尚未完成真实平台/设备验收；
- **未验证**：缺少运行环境、真实设备或外部发布条件；
- **阻塞**：同一外部阻塞条件连续出现且没有安全替代路径。

验证范围必须匹配变更范围。前端变更至少运行相关契约测试和生产构建；数据/启动器变更至少运行相关 Python 测试；发布变更必须运行对应 release/mobile preflight。真实安装包、签名、升级和 Android/iOS 设备验收不得用静态检查冒充。

## 6. Git 与工作树规则

- 直接在 `main` 上迭代，不为普通迭代创建分支。
- 提交应按模块或功能保持密集、可读；提交信息使用 `<type>(<scope>): <summary>`。
- 合并场景必须使用 `--no-ff`，严禁快进合并；普通直接提交不伪造合并提交。
- 推送前运行与改动匹配的测试，并在报告中记录提交哈希和远端状态。
- 用户明确保留的修改必须原样保留，不得暂存、覆盖或提交。当前明确保护项包括 `time-helper/desk/package-lock.json` 与用户提供的 `docs/HOTL/` 材料。
- 禁止用重置、强制覆盖或大范围删除来“整理”用户内容。

## 7. HOTL1 对齐检查

每个涉及主工作区的阶段报告都应复核：

- PH 是完整计划，TD 是单条快速待办，TH 是时间维度；三者融合协作但不合并成同一实体；
- 首页同时呈现三模块关键信息并提供深链；
- 桌面端利用宽屏分区布局，移动端采用适合触控的独立布局；
- 主题可切换并持久化，且不破坏 TH 丰富主题架构；
- 主界面不再提供日历功能入口；
- 启动、统一存档、导入导出及多语言边界有对应证据。

报告不能只写“符合 HOTL1”，必须指出具体文件、测试或运行结果。

## 8. 文档维护

规范变化必须先更新本文件并单独提交；普通实现报告只追加新文件，不重写历史报告来掩盖旧状态。阶段审计应引用相关报告和当前命令输出，并明确哪些事项仍需真实发布环境完成。
