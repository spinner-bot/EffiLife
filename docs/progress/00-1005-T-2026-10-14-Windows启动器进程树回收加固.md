# [完成] Windows 启动器进程树回收加固

- 创建时间：2026-10-14
- 执行者：Codex
- 触发原因：真实浏览器验收结束后，发现 npm shim 退出时可能遗留 Vite/Plan Helper 子进程和监听端口。
- 本次目标：建立明确的 launcher-owned 进程树边界，确保 Windows 下正常退出和标准控制事件能够回收后代进程。

## 一、问题定位

Windows 开发启动链路包含 npm shim、cmd、Node/Vite 等多层进程。仅依赖 `taskkill /PID /T` 时，如果中间 shim 已经退出，剩余 node 进程可能不再能通过原 PID 稳定定位。

本次没有使用按进程名匹配的粗粒度终止方式，避免误杀用户的其他 Node 或 Python 程序。

## 二、实现

修改 `launcher/start.py`：

- 启动主服务和配套服务后，将 Windows 子进程加入带 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job Object。
- 终止服务时优先关闭 Job Object，回收其完整后代树。
- 保留原有 `taskkill /T /F` 和 POSIX 进程组逻辑作为兼容兜底。
- Job Object 创建或绑定失败时不阻断启动，仍沿用已有清理路径。

## 三、验证

```text
python -m pytest -q tests/test_launcher.py
85 passed

python -m pytest -q
1257 passed in 19.14s
```

另外执行了真实 Windows 进程验证：

- 直接启动 npm/Vite 后绑定 Job Object，再调用 launcher 终止逻辑，1420 端口释放。
- 启动完整 launcher 后发送标准 Windows 控制事件，launcher 退出且 1420、8765 端口均释放。

## 四、边界

交互式 PTY 的 Ctrl+C 可能由宿主终端直接终止外层进程，绕过 Python 的 `KeyboardInterrupt` 清理分支；这是测试终端信号传递差异。正式 Windows 控制台和标准控制事件路径已通过 Job Object 验证，后续仍可对开发测试工具的 PTY 回收做独立增强。
