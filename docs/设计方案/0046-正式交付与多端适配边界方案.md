# 正式交付与多端适配边界方案

## 结论

`launcher/start.py`、`launcher/start.bat` 和 `launcher/start.sh` 仅用于开发、测试、回归和迁移，不属于正式产品启动方式。正式版本应由 Tauri 构建安装包并提供平台原生启动入口。

## 正式交付目标

- Windows：优先生成 NSIS 安装包，并保留便携版构建可能性。
- macOS：生成 `.app` / `.dmg`，处理签名与公证。
- Linux：根据发布渠道生成 AppImage，并评估 deb/rpm。
- Android/iOS：复用 Vue 统一前端与共享数据契约，使用 Tauri Mobile 能力或平台适配层提供文件、通知和生命周期接口。

## 必须解决的架构问题

1. **Plan Helper 运行时**：正式安装包不能依赖用户另行启动 Python HTTP 服务。需要将计划能力迁移到桌面内置 Rust/本地服务，或将 Python 服务作为受控 sidecar 随包分发并由 Tauri 管理生命周期。
2. **移动端数据**：移动端不能假设 `127.0.0.1:8765` 存在，计划能力必须使用内嵌实现或同源适配层。
3. **数据目录**：正式版本使用 Tauri 的应用数据目录和平台文件选择器，不能依赖项目目录或开发服务器目录。
4. **更新与签名**：发布前需要配置各平台签名、更新策略、权限声明和崩溃/迁移保护。
5. **统一配置**：开发环境的 `VITE_PLAN_HELPER_ORIGIN` 仅作为过渡；正式构建应切换到内嵌服务或同源 API，不把开发端口写入产品契约。

## 当前阶段边界

当前统一启动器只服务于功能开发和集成测试。先稳定统一前端、数据格式和跨模块契约，再进行正式运行时替换，避免把临时 HTTP companion 直接固化到安装包架构中。
