# 启动器诊断建议层方案

- 状态：[完成]
- 创建时间：2026-09-29
- 执行者：Codex
- 关联目标：统一启动与应用壳

## 1. 背景

launcher 的 `--diagnose` 已经能够输出运行时、端口、服务和二进制事实，但用户需要自行从原始 JSON 判断启动失败原因。正式包缺失、Node/npm 缺失、端口被非工作台服务占用等情况应该给出明确下一步。

## 2. 方案

在现有诊断 JSON 中增加两个只读字段：

- `issues`：当前会阻止或影响启动的问题，包含稳定的 `code`、`severity`、`message` 和 `hint`；
- `hints`：不阻塞当前开发启动，但对发布或迁移有帮助的提醒。

诊断仍不启动、停止或修改任何进程；原有模块状态字段保持不变。

## 3. 规则

- 开发模式缺少统一工作台可用运行时：记录阻塞问题；
- 正式模式缺少 Tauri 二进制或静态构建：记录阻塞问题；
- URL 端口已占用但健康检查失败：记录端口冲突问题；
- Rust/Cargo 缺失：作为发布提示，不阻塞已经存在的开发前端；
- 已运行且健康的服务不产生错误，继续使用现有复用逻辑。

## 4. 验收标准

- [x] `--diagnose` 输出可机器读取的 issues/hints。
- [x] 启动阻塞与发布提醒分级。
- [x] 诊断保持只读。
- [x] 覆盖开发、正式包、端口冲突和 Rust 缺失场景测试。
