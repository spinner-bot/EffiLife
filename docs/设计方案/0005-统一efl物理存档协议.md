# 统一 `.efl` 物理存档协议

**文档性质**：跨模块数据协议设计方案（实施前置）
**创建时间**：2026-09-25（Asia/Shanghai）
**适用范围**：common、time-helper、plan-helper、to-dos 的导入导出

## 1. 问题

项目中 Python 公共层和 time-helper 前端都使用 `.efl` 扩展名，但当前 ZIP 内部协议不同：公共层使用 `manifest.json + data/*.json`，前端使用单一 `archive.json`。同一扩展名不能代表两种互不兼容格式。

## 2. 统一协议

所有新导出的 `.efl` 使用：

```text
manifest.json
data/app.json
data/records.json
data/todos.json
data/plan_helper.json
README.txt
```

manifest 固定包含：

- `format: effilife.bundle`
- `format_version: 1.0.0`
- `created_at`
- `datasets`
- `metadata`

其中 `app` 保存 time-helper 配置、计划、设置、事件和打卡等应用数据；其它数据集按领域独立保存。

## 3. 向后兼容

- 导出只生成新协议。
- 导入优先读取 `manifest.json`；若不存在则读取旧版 `archive.json`。
- 旧版导入后恢复到统一内部模型，但再次导出会升级为新协议。

## 4. 安全与完整性

- manifest 声明的每个 dataset 必须存在且为有效 JSON。
- 未声明的数据文件不参与导入。
- 领域数据恢复仍由各自适配器/服务负责，不在 ZIP 层重写计划任务编号。

## 5. 验收条件

- Python 公共层生成的 `.efl` 可被 time-helper 识别。
- time-helper 新生成的 `.efl` 可被公共层 `read_bundle()` 读取。
- 旧版 `archive.json` 存档仍可导入。
- 数据集缺失或 manifest 损坏时给出明确错误。
