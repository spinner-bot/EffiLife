# TD–PH 计划关联稳定标识方案

## 问题

PH 任务同时存在稳定的 `internal_id` 和软删除后动态计算的 `display_id`。删除任务后，显示编号会压缩，例如原 A3 可能显示为 A2。若 TD 关联修复同时接受两种编号，原本指向已删除 A2 的关联会被误判为当前显示 A2，并错误指向原 A3。

## 决策

- TD 持久化的 `related_plan_task_id` 统一使用 PH 的 `internal_id`。
- `display_id` 只用于 PH/搜索/深链接的展示与人工定位，不参与 TD 关联存活判断。
- PH 交互 API 仍可兼容 display ID，由 PH 自己解析到内部槽位；这不改变模块边界。
- 启动修复只用活动任务的 `internal_id` 集合验证 TD 关联。明确失效的内部 ID 才会解除关联；计划服务不可用、仅有缓存或计划已归档时保留关联。
- PH 删除任务时已有的显式解除关联继续保留，启动修复作为异常中断或历史数据的兜底。

这样既保留了软删除的历史编号语义，也避免 TD 被动态显示编号重绑定到另一项任务。
