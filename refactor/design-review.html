11 产品设计审阅稿

  • 状态：待用户审计；尚未作为实现定稿

1. 协作方式与阅读说明

用户提供产品初衷、核心关系和关键取舍，Codex 据此撰写完整草案，自行拟定常规交互和技术细节。用户通过审计草案修正方案。提问集中在影响产品方向、无法从已有要求合理判断的问题上。

本文使用两类编号：

  • R：用户已明确的要求。保留原意，作为后续方案的依据。
  • P：Codex 提案。为形成可审阅的完整方案而拟定，供用户修改；列出提案不代表用户已经批准。

字段布局、默认值、按钮位置、录入时间格式等细节由 Codex 先拟，随具体页面设计补充。当前审计首先关注产品关系、内容层级与使用动线。

2. 设计初衷与产品定位

用户已明确R-001 起点与远期方向。# EffiLife 起源于作者未被现成软件满足的实际需求，并考虑长期产品化与商业化。当前先讨论产品本身。

用户已明确R-002 持续生活管理。# 产品面向个人持续、全方位的生活管理。其复合模型旨在适配现代人快节奏、多任务的城市生活，覆盖工作、生活和休息等方面。

用户已明确R-003 时间与事件两条主线。# 核心是将时间和事件合理关联。两条主线分别组织时间分配与事务推进，并能共同表达用户的实际行动。关联需要减少重复操作，同时保留两种视角的管理价值。

用户已明确R-004 零散待办的补充职责。# 待办管理订票、取快递、买盐等事项，保留其独立使用场景和既有优先排位算法。

用户已明确R-005 并行计划。# 用户可以同时推进多份主题明确的计划，借助时间视角了解每天的投入和生活分配，并处理日常待办。

用户已明确R-006 事件侧基本单元。# 一份 Plan 是围绕明确主题组织的整份计划，包含基本信息、计划内容和执行日志。保留条目定位、分组及近似树状层级的组织价值。

用户已明确R-007 进展日志。# log 是核心特色，支持记录具体子项取得进展但尚未完成的情况。一次推进与最终完成具有不同含义。

3. 统一录入方向

3.1 用户提出的要求与探索方向

用户已明确R-008 减少重复记录。# 用户不应每做一件事，都先进入时间侧记用时，再进入事件侧登记进展。

用户已明确R-009 统一入口。# 用户希望日常行动采用统一、醒目的录入入口，同时承接已纳入计划的行动和吃饭等未纳入计划的生活事件。

用户探索方向 · 具体规则待细化R-010 类别关联方向。# 用户提出一种可能方案：为计划条目指定时间侧类别，并支持从任意父节点统一指定下方子条目的类别，记录时自动归类。这是待细化的设计方向，具体继承、覆盖与存储规则由草案提出。

3.2 录入方案提案

Codex 提案 · 待审计P-001 以本次行动组织录入。# 设置全局“记录”主入口。用户填写本次做了什么及实际用时，可关联计划子项并记录进展；确认提交后，由软件维护两个视角的对应信息。

情境 时间侧表达 事件侧表达
推进某个计划子项，尚未完成 本次实际时间及类别 关联子项的进展日志，保留未完成状态
完成某个计划子项 本次实际时间及类别 记录完成状态；日志展示方式随页面草案细化
吃饭等独立生活事件 本次实际时间及类别 可独立记录，无需先创建主题计划

该表描述一次行动同时具有时间与事件信息时的处理。原有历史进展日志可以保留其内容和发生时刻，实际用时缺失时明确表示未知。

Codex 提案 · 待审计P-002 自动带出已有信息。# 选择计划条目后带出其名称、所属计划和时间类别，允许调整本次记录。统一入口保持同一套录入逻辑，并可使用当前页面已选中的条目作为初始上下文。

Codex 提案 · 待审计P-003 父节点提供批量类别设置。# 父节点展示操作范围；下方尚未指定类别的条目默认采用该类别，已有明确类别的条目保留原值，并提供显式覆盖选项。新增条目的默认类别采用最近上级指定值。具体规则待页面草案与数据方案共同审计。

Codex 提案 · 待审计P-004 时间填写采用事后补录作为默认方案。# 草案支持实际起止时间与时长之间的便捷填写，允许调整结束时间。计时操作与字段排列后续拟定，用户无需在当前阶段逐项选择。

4. 内容层级与使用动线

用户已明确R-011 为“看”专门设计。# 查看状态、浏览进展和理解信息本身就是完整的使用目的，需要专门的组件与界面。

用户已明确R-012 降低路径负担。# 高频操作应容易到达，减少进入三四层菜单、反复切换和复杂重复操作。内容层级、信息展示和交互共同组成使用动线。

4.1 一级结构提案

Codex 提案 · 待审计P-005 采用一套主导航与全局记录入口。# 桌面主导航初拟如下，名称、顺序与布局均可在审计中调整。

入口 主要职责 第一层应提供的内容
总览 了解当前生活与事务状态 今日时间分配、并行计划进展、需要处理的待办、最近行动
计划 组织并持续推进主题事务 并行计划、主题结构、具体子项、执行日志
时间 了解和安排时间投入 日期切换、当日分配与记录、历史时间信息
待办 收集与处理零散事项 待办清单、优先排位、临近截止事项、分类筛选
设置 管理产品行为与个性化配置 按用户目的组织的设置分区、主题与包管理、数据管理

记录主入口在各主页面保持稳定位置；相关内容页通过明确的对象链接衔接。计划和待办分别可直接进入，时间侧与事件侧通过共同记录和上下文链接关联。

日报、周报等专门回顾能力见远期目标。当前的总览与时间历史继续承接已有基础信息展示。

4.2 主要动线提案

Codex 提案 · 待审计P-006 围绕使用目的安排路径。#

使用目的 拟定路径 路径需要保留的信息
看目前的生活状态 打开总览即可查看主要信息，按需进入具体视角 当前日期与展示范围
看某项重要事务推进情况 总览中的计划摘要 → 该计划的结构与日志 计划身份、选中条目与最近进展
记录一次行动 全局记录入口 → 填写并提交 → 返回原场景 输入草稿、关联条目、原页面位置
从时间记录理解投入去向 时间记录 → 关联计划条目及其进展 原记录与时间范围
从计划理解已有投入 计划条目 → 关联执行日志与实际时间记录 条目身份及相关历史
处理零散事项 待办入口 → 收集、查看排位或处理事项 分类、筛选和清单位置

操作完成后更新对应视角，保留用户原来的浏览上下文。常用动作直接在相关内容附近呈现，较少使用的管理操作逐步展开。

4.3 为浏览设计的组件提案

Codex 提案 · 待审计P-007 建立可独立阅读的信息组件。# 优先设计每日时间分配、并行计划摘要、条目进展、执行日志流、待办摘要等组件。组件显示清楚的对象、时间范围、状态和必要说明，再提供进入详情或相关操作的位置。

总览各区呈现核心信息与变化，并能进入对应视角；编辑控件在用户开始相关操作后展开。日志内容保留进展描述，时间信息同时区分发生时刻与实际用时。

5. 视觉与交互方向

用户已明确R-013 现代、清爽、美观。# 界面需要达到成熟个人产品的品质，将信息展示与交互体验共同设计，支持长期舒适使用。用户明确反对旧界面类似简陋开发工具设置面板的体验。

Codex 提案 · 待审计P-008 默认视觉采用轻量桌面工作台方向。# 使用中性色表面、清楚的文字层级、适度的信息密度、稳定的分区与克制的强调色。通过分栏、列表和上下文详情利用桌面空间；交互动作就近出现。字号、间距、颜色与控件状态由统一体系管理。

字体沿用已决定的 Inter Variable 与 Noto Sans SC 子集；组件底层沿用 Reka UI。具体色值、布局尺寸和动效由 Codex 在设计地基与页面草案中提出。

Codex 提案 · 待审计P-009 先确定一套完整的默认界面。# 以总览为试点，将浏览状态、主要操作与进入详情的路径一起展示，审计后推广到其他页面。旧 25 套主题按已有决策保留，并通过后续主题运行时与迁移方案承接。

6. 连续使用与数据关联提案

Codex 提案 · 待审计P-010 一次提交具有完整结果。# 一次行动涉及时间记录与计划信息时，保存结果明确反映整个操作。失败保留草稿；出现部分写入时，由软件维护可恢复的操作状态，重试应避免产生重复记录。具体事务或补偿机制由数据与实现方案决定。

Codex 提案 · 待审计P-011 历史关联可追溯。# 行动、日志、条目与时间记录之间使用稳定引用。修改实际用时后，对应统计更新；修改进展描述后，对应日志展示更新。删除或解除关联的影响需要向用户说明，并在数据方案中定义恢复规则。

Codex 提案 · 待审计P-012 连续积累覆盖跨日使用。# 页面支持查看历史日期，保留多次推进同一条目的过程；跨日的记录按实际日期与时间表达。累计实际投入、计划预计用时和条目完成状态分别表达。

本文定义产品行为与数据关系的要求。数据 schema、存储位置及与现有协议的迁移方案在后续技术文档中具体设计。

6.1 多端与系统级可扩展性

用户已明确R-014 从开始考虑多端。# 产品远期需要多端适配，当前即应在系统架构中考虑可扩展性。首期交付以桌面端为主，架构需要明确平台能力与业务规则的边界。

用户已明确R-015 资源与能力可扩展。# 多语言、主题、字体等系统需要支持后续新增和替换，避免初期把固定选项和具体实现散布到各处。用户要求采用模块化思维与系统级架构设计。

Codex 提案 · 待审计P-013 通过共同契约与适配器组织系统。# 领域规则、应用服务、平台与存储适配、展示交互、资源与扩展系统分别承担明确职责；不同端遵循一致的记录与关联语义，采用适合设备的界面动线。

Codex 提案 · 待审计P-014 语言、主题与字体通过登记和加载机制扩展。# 界面从注册目录生成选项，资源通过稳定标识与语义角色引用，加载、切换和失败回退由对应服务统一管理。已有字体决定作为默认资源，后续新增字体走同一机制。

完整职责划分与扩展验收提案见 13-system-architecture.md。

7. 验收场景提案

以下场景用于后续页面与实现审计，不表示当前代码已经具备这些行为：

  1. 用户打开总览，直接了解当天时间分配、多个主题计划进展与待办情况。
  2. 用户为一个尚未完成的计划子项记录实际投入与进展，只需提交一次；时间侧与日志侧都能看到相应信息。
  3. 用户记录吃饭等生活事件，可以直接完成录入。
  4. 用户通过父节点为下方条目统一设置时间类别，并能理解已有类别的处理范围。
  5. 用户从某条时间记录进入关联计划，能定位到对应条目与进展；返回后保留原来的浏览位置。
  6. 保存失败时，用户保有已填写内容和清楚的恢复操作，重试成功后没有重复记录。
  7. 用户仅浏览时，能够完整理解概览、分配和进展，无需进入编辑流程。
  8. 新增语言、主题或字体时，通过资源与登记机制接入；核心页面和业务流程继续使用共同契约。

现有七档视口、WCAG AA、视觉回归和主题切换质量门槛继续作为重构依据，具体见 02-refactor-process.md。

8. 后续审计与远期目标

本稿首先供用户审计以下三处：

  1. 产品定位与时间、事件、待办的关系是否准确；
  2. 总览、主导航与统一录入是否形成合理的日常使用路径；
  3. 默认视觉方向是否符合长期使用的预期。

用户可以按 R/P 编号修改。Codex 根据反馈完善页面方案，主动检查跨章节影响，常规细节先形成具体提案。

产品化与商业化、日报/周报、智能穿戴、小型 AI agent、语音输入与后续多端交付统一记录于 12-long-term-goals.md。

13 多端与可扩展系统架构提案

  • 日期：2026-11-10
  • 作者：Codex (sqs_A100)
  • 状态：用户已明确架构约束；下文的职责划分与验收方案为 Codex 提案，待审计
  • 依据：产品设计审阅稿、D-029、D-030

1. 用户明确的架构约束

  1. 产品远期需要多端适配，从一开始就考虑可扩展性。
  2. 多语言、主题、字体等系统需要支持后续扩展，避免因初期固定实现而在扩展时大改。
  3. 采用模块化思维，先做系统级架构设计，再安排具体功能实现。

首期交付仍以桌面端为主。多端适配在当前架构阶段形成边界和契约，其他客户端的实际交付目标与排期后续确定。

2. 职责划分提案

层次 职责 主要约束
领域规则 主题计划、条目、进展日志、时间分配、待办及其关联语义 表达业务规则，采用明确的标识与数据契约
应用服务 统一录入、修改、查询、归档等完整使用操作 组织验证、关联写入、结果反馈和恢复，供不同入口与客户端调用
数据与平台适配 存储、文件选择、导入导出、通知、设备能力及现有服务调用 封装各运行环境的具体实现，向上提供稳定接口与能力状态
展示与交互 信息组件、使用动线、桌面或触屏布局 使用应用服务和查询结果，针对设备特点组织信息与操作
资源与扩展系统 语言、主题、字体、资源包、功能扩展 统一登记、加载、校验、生命周期和回退，通过受控接口协作

这些是单一产品内部的职责边界。文件组织、接口名称及具体共享代码方式在实现设计中确定。

领域规则与应用服务通过接口使用存储及平台能力，界面通过应用服务操作数据。首次实现即约束依赖方向，避免文件系统、Tauri 调用或特定服务地址扩散到页面和业务规则中。

3. 多端适配

3.1 业务语义与设备交互

不同客户端遵循相同的计划、日志、时间、待办和记录关联语义。具体代码可以共享，也可以通过同一版本化契约与行为用例保持一致；现阶段不强制所有现有 Python、Rust、TypeScript 逻辑迁入同一种语言。

桌面与移动端可以采用适合各自屏幕、键盘、指针或触屏的导航和记录入口，调用同一语义的应用操作。组件与 token 体系承载公共规则，平台壳负责设备特有交互。

3.2 平台能力接口

应用统一查询平台能力，再决定可用操作和反馈方式。文件选择、文件分享、通知等由适配器实现；明确区分可用、不可用、受限与失败。

当前桌面 Plan Helper sidecar 的接入需要封装在服务适配器内。未来客户端根据自身环境提供等价业务能力，核心动线依赖应用服务的能力契约。存储适配同样集中，具体 schema 与迁移在数据方案中制定。

多端适配、跨设备数据同步与云端服务分别定义范围。同步策略及账号系统在后续有明确需求时设计。

4. 多语言系统

语言通过统一注册目录描述：稳定语言标识、显示名称、文字方向、格式化规则与资源加载方式。导航、组件、主题及功能包的显示文字使用资源键或本地化元数据，业务身份保持稳定。

新增语言主要增加语言资源与注册信息。日期、数字、复数、断行和文字方向通过共同的本地化与布局能力处理，语言选择器由已注册项目生成。语言包缺失字段时按明确的回退链处理。

用户创建的计划名称和日志内容保留原文。语言切换影响显示资源与格式，语言显示名不充当类别、主题或业务对象的标识。

5. 主题系统

内置主题与后续主题包沿用共同的 manifest、解析和权限机制，见 03、04与 09。

页面和组件依赖语义 token 与明确的样式扩展点。新增主题主要增加包内容和登记信息，主题选择界面由注册表生成，包的加载、切换、卸载与失败回退由主题运行时统一处理。

L0–L2 遵循既定布局边界；L3 的布局与数据能力通过宿主 API 和沙箱提供。模块化扩展继续遵循既有权限分层。

6. 字体与资源系统

Inter Variable 与 Noto Sans SC 子集作为已有决定的默认资源。字体通过统一目录描述资源来源、许可、字重、覆盖文字范围与回退规则；组件引用正文字体、标题字体、等宽字体等语义角色。

字体加载与释放、加载状态和失败回退由字体服务管理。语言、主题或资源包可通过已定义的资源引用机制关联字体，具体允许范围与授权遵循包规范。

新增字体主要调整资源与目录登记，界面中的字体选择由登记信息生成。组件通过角色和 token 获取字体，布局在字体加载和回退时保持可读与可操作。

7. 新能力与统一录入

日报/周报、智能穿戴、自然语言 agent 与语音输入通过各自模块接入应用服务，使用明确的输入输出与能力声明。应用维护它们所需的查询、记录提交和生命周期接口，具体实现按远期目标推进。

自然语言和语音未来可以生成录入草稿，复用统一录入的校验、关联提交与结果反馈。智能穿戴的数据来源、时间信息和确认方式在接入方案中定义，以便追溯记录来源。

统一录入服务负责一次行动的关联处理，界面和后续扩展调用同一语义的操作。依赖版本和能力要求通过元数据表达，扩展失败按宿主定义的结果与恢复流程处理。

8. 持久化、版本与兼容

资源与扩展引用采用稳定标识；本地包与跨设备引用遵循 09 包注册表 的稳定 ID、本地 ID 与重新解析规则。

语言、主题、字体等配置有明确 schema 版本、默认值和缺失资源回退。读取旧配置与旧存档时通过迁移适配处理，导入结果说明可恢复内容及缺失依赖。

数据层的具体表结构、存储引擎与迁移实现另行形成方案。当前先约束引用、边界和行为，保持后续替换适配器与演进格式的空间。

9. 架构验收提案

实现设计与阶段验收使用以下场景检查扩展成本：

  1. 新增一门语言，主要修改资源与登记项，导航及通用控件正确显示并适配文字方向。
  2. 安装新主题，解析器按已有契约加载，页面正确消费 token 和权限能力。
  3. 新增一套字体，登记后可供既定字体角色使用，加载失败有可读回退。
  4. 接入另一种存储或平台适配器，计划、日志和统一录入的业务语义保持一致。
  5. 在另一类设备上采用不同入口布局，继续调用相同语义的记录操作并得到一致的关联结果。
  6. 增加一种未来录入来源，可以复用既有的草稿校验和提交能力。

每阶段选择与实际变更有关的场景验收。当前文档给出设计约束与提案，实际支持程度由后续实现和验证记录说明。

1. 产品定位与共同基础

EffiLife 起源于作者未被现成软件满足的实际需求，同时考虑长期产品化与商业化。产品面向个人持续、全方位的生活管理，关注现代人快节奏、多任务城市生活中的长期使用。

产品以时间和事件两条相互关联的主线为核心，以零散待办补充日常事务管理：

  • 时间主线帮助用户了解和安排每天的时间分配，兼顾工作、生活和休息。
  • 事件主线围绕明确主题组织整份计划，支持多个计划并行推进。
  • 待办承接订票、取快递等需要及时处理的零散事项。

计划中的 log 是重要的过程记录：具体子项取得进展但尚未完成时，可以记录日志，保留条目关联、发生时间和进展内容。日志发生时刻与一次行动的实际用时具有不同含义，后续关联设计需要保留这一差别。

已有定位说明见 H 文档。本轮补充的持续生活管理定位，是以下远期目标的共同依据。
