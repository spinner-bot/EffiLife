# 13 多端与可扩展系统架构提案

- 日期：2026-11-10
- 作者：Codex  (sqs_A100)
- 状态：用户已明确架构约束；下文的职责划分与验收方案为 Codex 提案，待审计
- 依据：[产品设计审阅稿](11-user-design.md)、D-029、D-030

## 1. 用户明确的架构约束

1. 产品远期需要多端适配，从一开始就考虑可扩展性。
2. 多语言、主题、字体等系统需要支持后续扩展，避免因初期固定实现而在扩展时大改。
3. 采用模块化思维，先做系统级架构设计，再安排具体功能实现。

首期交付仍以桌面端为主。多端适配在当前架构阶段形成边界和契约，其他客户端的实际交付目标与排期后续确定。

## 2. 职责划分提案

| 层次 | 职责 | 主要约束 |
|---|---|---|
| 领域规则 | 主题计划、条目、进展日志、时间分配、待办及其关联语义 | 表达业务规则，采用明确的标识与数据契约 |
| 应用服务 | 统一录入、修改、查询、归档等完整使用操作 | 组织验证、关联写入、结果反馈和恢复，供不同入口与客户端调用 |
| 数据与平台适配 | 存储、文件选择、导入导出、通知、设备能力及现有服务调用 | 封装各运行环境的具体实现，向上提供稳定接口与能力状态 |
| 展示与交互 | 信息组件、使用动线、桌面或触屏布局 | 使用应用服务和查询结果，针对设备特点组织信息与操作 |
| 资源与扩展系统 | 语言、主题、字体、资源包、功能扩展 | 统一登记、加载、校验、生命周期和回退，通过受控接口协作 |

这些是单一产品内部的职责边界。文件组织、接口名称及具体共享代码方式在实现设计中确定。

领域规则与应用服务通过接口使用存储及平台能力，界面通过应用服务操作数据。首次实现即约束依赖方向，避免文件系统、Tauri 调用或特定服务地址扩散到页面和业务规则中。

## 3. 多端适配

### 3.1 业务语义与设备交互

不同客户端遵循相同的计划、日志、时间、待办和记录关联语义。具体代码可以共享，也可以通过同一版本化契约与行为用例保持一致；现阶段不强制所有现有 Python、Rust、TypeScript 逻辑迁入同一种语言。

桌面与移动端可以采用适合各自屏幕、键盘、指针或触屏的导航和记录入口，调用同一语义的应用操作。组件与 token 体系承载公共规则，平台壳负责设备特有交互。

### 3.2 平台能力接口

应用统一查询平台能力，再决定可用操作和反馈方式。文件选择、文件分享、通知等由适配器实现；明确区分可用、不可用、受限与失败。

当前桌面 Plan Helper sidecar 的接入需要封装在服务适配器内。未来客户端根据自身环境提供等价业务能力，核心动线依赖应用服务的能力契约。存储适配同样集中，具体 schema 与迁移在数据方案中制定。

多端适配、跨设备数据同步与云端服务分别定义范围。同步策略及账号系统在后续有明确需求时设计。

## 4. 多语言系统

语言通过统一注册目录描述：稳定语言标识、显示名称、文字方向、格式化规则与资源加载方式。导航、组件、主题及功能包的显示文字使用资源键或本地化元数据，业务身份保持稳定。

新增语言主要增加语言资源与注册信息。日期、数字、复数、断行和文字方向通过共同的本地化与布局能力处理，语言选择器由已注册项目生成。语言包缺失字段时按明确的回退链处理。

用户创建的计划名称和日志内容保留原文。语言切换影响显示资源与格式，语言显示名不充当类别、主题或业务对象的标识。

## 5. 主题系统

内置主题与后续主题包沿用共同的 manifest、解析和权限机制，见 [03](03-theme-and-permission-system.md)、[04](04-package-formats.md)与 [09](09-package-registry.md)。

页面和组件依赖语义 token 与明确的样式扩展点。新增主题主要增加包内容和登记信息，主题选择界面由注册表生成，包的加载、切换、卸载与失败回退由主题运行时统一处理。

L0–L2 遵循既定布局边界；L3 的布局与数据能力通过宿主 API 和沙箱提供。模块化扩展继续遵循既有权限分层。

## 6. 字体与资源系统

Inter Variable 与 Noto Sans SC 子集作为已有决定的默认资源。字体通过统一目录描述资源来源、许可、字重、覆盖文字范围与回退规则；组件引用正文字体、标题字体、等宽字体等语义角色。

字体加载与释放、加载状态和失败回退由字体服务管理。语言、主题或资源包可通过已定义的资源引用机制关联字体，具体允许范围与授权遵循包规范。

新增字体主要调整资源与目录登记，界面中的字体选择由登记信息生成。组件通过角色和 token 获取字体，布局在字体加载和回退时保持可读与可操作。

## 7. 新能力与统一录入

日报/周报、智能穿戴、自然语言 agent 与语音输入通过各自模块接入应用服务，使用明确的输入输出与能力声明。应用维护它们所需的查询、记录提交和生命周期接口，具体实现按远期目标推进。

自然语言和语音未来可以生成录入草稿，复用统一录入的校验、关联提交与结果反馈。智能穿戴的数据来源、时间信息和确认方式在接入方案中定义，以便追溯记录来源。

统一录入服务负责一次行动的关联处理，界面和后续扩展调用同一语义的操作。依赖版本和能力要求通过元数据表达，扩展失败按宿主定义的结果与恢复流程处理。

## 8. 持久化、版本与兼容

资源与扩展引用采用稳定标识；本地包与跨设备引用遵循 [09 包注册表](09-package-registry.md) 的稳定 ID、本地 ID 与重新解析规则。

语言、主题、字体等配置有明确 schema 版本、默认值和缺失资源回退。读取旧配置与旧存档时通过迁移适配处理，导入结果说明可恢复内容及缺失依赖。

数据层的具体表结构、存储引擎与迁移实现另行形成方案。当前先约束引用、边界和行为，保持后续替换适配器与演进格式的空间。

## 9. 架构验收提案

实现设计与阶段验收使用以下场景检查扩展成本：

1. 新增一门语言，主要修改资源与登记项，导航及通用控件正确显示并适配文字方向。
2. 安装新主题，解析器按已有契约加载，页面正确消费 token 和权限能力。
3. 新增一套字体，登记后可供既定字体角色使用，加载失败有可读回退。
4. 接入另一种存储或平台适配器，计划、日志和统一录入的业务语义保持一致。
5. 在另一类设备上采用不同入口布局，继续调用相同语义的记录操作并得到一致的关联结果。
6. 增加一种未来录入来源，可以复用既有的草稿校验和提交能力。

每阶段选择与实际变更有关的场景验收。当前文档给出设计约束与提案，实际支持程度由后续实现和验证记录说明。
