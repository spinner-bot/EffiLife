# 06 归档区结构与代际快照

## 1. 目标

- 把不再参与开发的代际版本集中到单一归档区，而不是散落在各模块目录。
- 归档内容可追溯、可读、可对照，但不参与构建、测试与发布。
- 1 代单文件应用与 2 代最终版本都进入归档；3 代是当前开发主线。

## 2. 目录结构

```
archive/
├── README.md                       归档总览、规则、代际索引
├── v1-time-helper/
│   ├── README.md                   1 代说明、运行方式、已知限制
│   └── time-helper/
│       └── 浪兮效率时钟.py          1 代单文件 Tkinter 应用
├── v2-unified-workspace/
│   ├── README.md                   2 代说明；重构完成后补齐快照信息
│   └── (重构完成后放入 2 代最终源码快照)
└── misc/
    ├── README.md
    └── plan-helper/
        ├── README.md
        └── test.py                 早期个人练习脚本，不参与测试
```

## 3. 各代际说明

### 1 代：`archive/v1-time-helper/`

- 内容：`time-helper/python/浪兮效率时钟.py`（约 115 KB，单文件 Tkinter）。
- 归档时机：可以立即归档；它已不参与统一工作台构建。
- README 需包含：用途、运行方式（Python 3.6+）、数据目录、已知限制、归档日期。
- 归档后不再修改。

### 2 代：`archive/v2-unified-workspace/`

- 内容：本次重构开始前的最后一个 2 代状态。
- 归档时机：在 3 代合并回 `main` 之前，从当时的 `main`（或基线分支）生成快照。
- 建议包含：
  - 源码（不含 `node_modules`、构建产物、运行时数据）；
  - 关键文档：README、集成文档、版本规范、设计文档；
  - 构建与发布配置；
  - 最后提交 hash、日期、版本号；
  - 已知问题与验收边界；
  - 安装包/构建产物的路径与 SHA-256（二进制不入 git，记录位置与校验和）。
- README 需说明：这是历史快照，不接收修复，不参与发布。

### misc：`archive/misc/`

- 早期练习脚本、一次性样例、不可归类但需要保留的文件。
- 每个子目录有 README，说明来源、日期、是否可运行。
- `plan-helper/test.py` 属于此类：不是测试套件的一部分（`pytest.ini` 只收集 `tests/`），保留原样。

## 4. 归档规则

1. **单一入口**：所有历史代际只在 `archive/` 下，不再在模块目录里另建归档目录。
2. **不可变**：归档后不修改、不修复、不更新依赖；如需修复，在新主线进行。
3. **不参与构建**：`archive/` 不进入前端构建、Python 测试、发布矩阵。
4. **README 必需**：每个代际/子目录都有说明，至少包含来源、日期、用途、限制。
5. **不存运行时数据**：用户数据、缓存、`node_modules`、构建产物不入归档。
6. **二进制只留元数据**：安装包不入 git，记录路径与校验和。
7. **密集提交**：创建目录、写 README、移动文件、更新引用分别提交。

## 5. 需要同步更新的引用

- 根 `README.md` 的“实现版本”表：1 代路径从 `time-helper/python/` 改为 `archive/v1-time-helper/`，并标注“已归档，不参与当前构建”。
- `plan-helper/archive/` 目录在迁移完成后删除，避免出现第二个归档入口。
- 任何脚本/文档若引用旧路径，一并更新；测试若引用旧路径，改为断言归档存在或移除。
