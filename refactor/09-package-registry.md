# 09 包注册表与 ID 分配

- 日期：2026-10-27
- 状态：已确认（D-025），细节待设计文档补充

## 1. 原则

**ID 属于软件，不属于主题。**

- 主题包只提供内容与元数据：名称、版本、作者、许可、权限声明、校验和。
- 安装时由软件注册表分配 ID；ID 是本地安装编号，不是全局身份。
- 换设备、重装、重新导入都可能得到新 ID。
- 注册表同时负责权限登记、启停状态、激活指针、审计与墓碑。

本地第三方作者不需要协调全局唯一 ID；系统/云端包的稳定编号由对应渠道分配。

## 2. ID 区段

按 kind 独立发号（theme / resource / function / data）：

| 区段 | 用途 | 编号性质 |
|---|---|---|
| 0–999 | 系统自带包 | 固定，跟随包 |
| 1000–9999 | 系统可选包 | 固定，跟随包 |
| 10000–99999 | 云端扩展包（当前无服务器，预留） | 固定，跟随包 |
| 100000–999999 | 本地扩展包（文件导入） | 动态分配，仅本机有效 |

规则：

- **0–99999 的编号跟随包**：系统自带、系统可选与云端扩展的 ID 是稳定的，重装/升级/换设备后保持同一 ID。
- **100000–999999 为本地扩展**：导入时由注册表动态分配；换设备、重装、重新导入都可能得到新 ID。
- 本地包不表达 ID；注册表内部编号即可。来源（内置/云端/本地）由安装渠道决定。
- 云端区段当前只预留，不分配；未来有服务器后由服务端分配并下发。
- 已卸载的本地 ID 进入墓碑，不复用。
- ID 一旦分配，在本次安装生命周期内不变。
- 设置、激活指针、审计记录引用注册表 ID，不引用文件名；跨设备引用只对 0–99999 的稳定 ID 直接有效。

按 kind 独立发号意味着 theme 的 `5` 与 resource 的 `5` 不冲突；如果希望全局唯一，需要在数据层定稿时改为单一序列。

## 3. 注册表记录

```json
{
  "schemaVersion": 1,
  "nextId": 10003,
  "entries": [
    {
      "id": 1,
      "kind": "theme",
      "name": "Paper & Ink",
      "version": "1.0.0",
      "author": "EffiLife",
      "source": "builtin",
      "path": "builtin://paper-ink",
      "checksum": "sha256:...",
      "status": "active",
      "enabled": true,
      "requiredPermissions": ["appearance.tokens", "appearance.css"],
      "grantedPermissions": ["appearance.tokens", "appearance.css"],
      "compatibility": {
        "formatVersion": 1,
        "apiVersion": 1,
        "minAppVersion": "3.0.0"
      },
      "installedAt": "2026-01-01T00:00:00Z",
      "updatedAt": "2026-01-01T00:00:00Z"
    }
  ],
  "activeByKind": { "theme": 1 },
  "tombstones": [1024, 1031],
  "audit": []
}
```

字段说明：

- `id`：注册表分配，本地有效。
- `kind`：包类型；各 kind 独立发号。
- `source`：builtin / official / third-party。
- `status`：active / disabled / broken / pending-consent。
- `requiredPermissions`：来自包 manifest。
- `grantedPermissions`：用户实际授权，宿主写入。
- `checksum`：内容指纹，用于完整性与重复识别。
- `activeByKind`：当前主题、资源包、功能包。

## 4. 生命周期

1. **安装**：读取包 → 校验格式 → 判定来源与区段 → 稳定包校验/沿用其 ID，本地包分配 100000+ 的新 ID → 写入注册表 → 权限确认 → 启用。
2. **启用**：解析器按 ID 加载；失败则标记 `broken` 并回退。
3. **禁用**：停止沙箱、恢复安全主题，保留注册表记录。
4. **卸载**：删除包与缓存，ID 进入墓碑，不回收。
5. **升级**：见第 6 节“更新识别”。
6. **重装**：若按新包处理，分配新 ID；若识别为同一主题的升级，保留原 ID。

## 5. 权限登记

权限四方分离：

| 来源 | 负责 |
|---|---|
| 宿主能力目录 | 定义能力、级别、版本 |
| 包 manifest | 声明必需/可选能力 |
| 注册表 | 记录用户实际授权、时间、撤销 |
| 解析器 | 计算生效权限 = 必需 ∩ 授权 ∩ 应用策略 |

规则：

- 注册表由宿主独占，主题（包括 L3）不能直接写注册表、授权记录或审计日志。
- 升级后如果必需能力增加，标记 `pending-consent` 并禁用，直到用户重新确认。
- 撤销授权立即生效；依赖该能力的主题进入 `disabled`。
- L3 写操作进入审计；注册表本身不在 L3 可写的数据域内。

## 6. 更新识别

- **0–99999（系统/云端）**：ID 稳定，直接按 ID 判定为同一主题的新版本；版本号用于比较新旧。
- **100000+（本地）**：ID 每次安装可能不同，按 `name + author` 匹配并询问用户是更新还是并存；可选 `slug` 或内容指纹作为辅助。
- 本地包不参与稳定 ID 体系；它不需要知道、也不应该依赖自己的注册表 ID。

## 7. 跨设备与存档

- **0–99999**：稳定 ID 可直接随设置/存档迁移；换设备后只要同一主题存在，引用仍然有效。
- **100000+**：本地 ID 只在本机有效。存档应保存名称+作者+校验和，导入时按本机注册表重新解析；或提示用户重新导入主题包。
- 这与数据大改直接相关，等 schema 定稿后决定具体字段。

## 8. 不做

- 不要求本地第三方作者申请全局唯一 ID；
- 不允许主题修改注册表或自己的授权；
- 不回收已卸载的 ID。

## 9. 与数据大改的关系

注册表是数据层的一部分：schema、存储位置、迁移策略都应在数据大改中统一定义。本文件只固定“ID 由软件分配、注册表管权限”的原则；具体表结构在数据 schema 定稿后实现。
