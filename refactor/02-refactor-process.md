# 02 重构流程与质量门槛

## 1. 总体原则

1. **质量优先**：重构期间可以不可用；不以“先能跑”为由保留临时的坏结构。
2. **表现层重写，不是全仓库重写**：保留服务、数据协议、测试与发布链路。
3. **阶段可验收**：每个阶段有明确退出标准；不设死线，不按时间倒推质量。
4. **基线可回退**：开始前保留 2 代最后状态的分支/归档，任何阶段都能对照。
5. **密集提交**：每个文件创建/修改、每次目录结构调整单独 commit；阶段提交落在 `feat/frontend-platform`，阶段验收后用 `--no-ff` 合并回 `main`。

## 2. 分支与提交策略（已决定，D-022）

本次是跨多周的平台级重写，采用长分支方案：

- 创建长期分支 `feat/frontend-platform`，阶段内允许不绿；
- 每个阶段通过验收后，用 `git merge --no-ff` 合并回 `main`；
- 保留 `legacy/frontend-2026-10-26` 基线分支，确保可对照；
- 提交粒度：一个文件或一个完整小改动一次 commit；目录移动单独提交；
- 文档工作区（`refactor/`、`archive/`）继续直接落 `main`，按文件拆分提交。

## 3. 阶段划分

### Phase 0：基线与规范

**产出**
- 基线分支/归档快照
- 《前端平台分层规范》
- 《主题包与权限 spec v1》
- 《包格式 spec》（d3el / r3el / t3el / f3el）
- 《旧主题迁移映射》
- 《页面级完成定义》
- 选定视觉方向与质量门槛

**退出标准**
- 用户确认所有阻塞性决策（见 07）
- 不写业务代码

### Phase 1：设计地基

**产出**
- token 体系：颜色角色、字号、间距、圆角、阴影、透明度、z-index
- 字体加载策略（内置或系统栈）
- motion token
- 布局原语：AppShell / PageHeader / SplitLayout / Stack / Cluster / Grid / Toolbar / Section / List / FormRow / EmptyState
- 组件画廊页（内部路由即可）

**退出标准**
- 新代码无硬编码颜色/字号
- 原语可覆盖所有现有页面结构

### Phase 2：组件库

**产出**
- Button / Input / Select / Card / Dialog / Tabs / Tooltip / Toast / Menu / EmptyState / Skeleton
- 交互底层优先使用 headless 组件（待确认）
- 全状态：默认/悬停/聚焦/按下/禁用/加载/错误

**退出标准**
- 键盘与焦点路径完整
- 对比度检查通过
- 页面不再定义自己的控件外观

### Phase 3：应用壳与导航

**产出**
- 桌面侧栏 + 移动底栏的统一 AppShell
- 统一导航与命名；移除页内重复模块标签与模块徽标；合并设置入口
- 路由过渡、页面标题、焦点管理
- 窗口矩阵：320 / 390 / 768 / 1024 / 1280 / 1440 / 1920

**退出标准**
- 七档无横向溢出、无元素重叠
- 布局在所有主题下保持一致

### Phase 4：试点页（首页）

**产出**
- 首页按新体系重写
- 一次完整人工视觉评审

**退出标准**
- 达到“页面级完成定义”
- 评审结论确认后再复制到其他页面

### Phase 5：页面迁移

顺序：首页 → 计划 → 计划详情 → 待办 → 记录 → 设置（合并为一页分区）→ 音频/动效/事件 → 打卡/日详情。

**退出标准**
- 所有页面只使用平台组件与原语
- 旧视图目录清零
- 空/加载/错误/草稿保护状态统一

### Phase 6：主题运行时与包管线

**产出**
- 包读取、manifest 校验、权限解析、token 解析
- `.t3el` 导入/预览/安装/升级/卸载
- 主题切换过渡
- 3–5 套参考主题包

**退出标准**
- 非法包被拒绝
- 主题切换无布局跳动
- 参考主题全页面验收

### Phase 7：旧主题迁移

- 25 套主题全部保留，转换为主题包
- 先迁移 5 套作为规范样例，其余分批
- 旧配置走兼容映射

**退出标准**
- 全部旧主题在新运行时可用
- 无主题依赖源码分支

### Phase 8：质量门禁与收尾

**产出**
- 视觉回归、重叠检测、无障碍、性能预算
- 删除旧代码与旧主题引擎
- 更新文档与受影响的测试
- 版本切到 3.0.0，建立变更记录

**退出标准**
- 质量门禁全绿
- 无 legacy 引用
- 归档 2 代最终版本

## 4. 页面级完成定义

一个页面同时满足以下条件才算完成：

- 只用平台组件与布局原语；无页面私有控件样式
- 空/加载/错误/禁用/草稿状态完整
- 七档窗口无溢出、无重叠
- 浅色/深色 + 3 套参考主题下布局一致
- 键盘可完成主路径，焦点可见
- 视觉回归截图通过
- 无控制台 error；warning 须清零或登记原因

## 5. 质量门禁

| 门禁 | 要求 |
|---|---|
| 布局 | 七档视口（320/390/768/1024/1280/1440/1920）零横向溢出；自动检测元素重叠 |
| 主题隔离 | L0–L2 不得改变几何布局；L3 任意布局单独冒烟并必须可恢复 |
| 无障碍 | WCAG AA；键盘可达；焦点可见 |
| 动效 | 120/180/240ms；只动 transform/opacity；尊重 reduced-motion |
| 视觉回归 | 核心路由 × 视口 × 参考主题截图对比 |
| 性能 | 主题切换无布局跳动；效果层有帧率预算 |
| 测试 | 解析器/包校验/权限/迁移有单测；行为覆盖不回退 |

## 6. 测试策略

- **保留**：现有 Python 行为测试与发布门禁。
- **更新**：直接断言旧 DOM/CSS/源码结构的契约测试（例如选择器、默认字符串），在对应页面迁移时同步改写，不删除覆盖。
- **新增**：
  - 包解析与 schema 校验；
  - 权限启用/禁用；
  - ZIP 路径穿越、符号链接、压缩比异常；
  - token 对比度；
  - 主题兼容版本；
  - 视觉回归与重叠检测。
- **不新增**：只为旧结构续命的测试。

## 7. 与数据大改的协作

- 本重构不先改数据结构与存储布局。
- 主题持久化字段（`themeId` / 版本 / options）、旧 `Config.theme` 迁移、`.efl` 兼容，等数据 schema 定稿后实现。
- 如果数据大改先完成，本工作区更新接口假设后再进入 Phase 6。
- 页面布局与运行逻辑的最终方案以用户设计文档为准；在此之前只做不依赖该方案的地基与组件。
