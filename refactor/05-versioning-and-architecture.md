# 05 版本策略与单一软件架构

## 1. 版本决定

- 本次重构完成并合并后，产品版本定为 **3.0.0**。
- 3.0.0 起，EffiLife 按**单一软件**开发和发布，不再存在“三个模块”的产品概念。
- 以往版本记录未生效（构建产物显示 `v0.0.0`），从 3.0.0 起建立真实、可验证的版本记录。

## 2. “取消三模块”的含义

取消的是**产品结构与用户认知**，不是领域划分：

- 用户界面只保留一套导航、一套设置、一套数据与存档概念。
- TH / PH / TD 退化为内部领域（时间、计划、待办），不再以模块名、模块徽标、模块入口出现在主界面。
- 不再维护三套独立版本号、三套 CHANGELOG、三套发布 tag。
- 内部代码可以暂时保留领域命名，但不得再以“模块”对外表达。

## 3. 版本文件与标签（计划，尚未执行）

现状：

- `time-helper/VERSION` 1.7.0
- `plan-helper/VERSION` 0.5.1
- `to-dos/VERSION` 0.5.0
- `time-helper/desk/package.json` 1.7.0
- `docs/spec/版本管理规范.txt` 仍按模块描述

3.0.0 切换时建议：

1. 在仓库根建立唯一 `VERSION` 文件，内容 `3.0.0`。
2. 根 `CHANGELOG.md` 成为唯一产品变更记录。
3. 发布 tag 使用 `v3.0.0`，不再使用 `time-helper/v...` 等模块 tag。
4. 三个模块的 `VERSION` 与 `CHANGELOG.md` 在归档时保留历史，不再参与构建与发布。
5. 更新 `docs/spec/版本管理规范.txt`，把“模块独立版本”改为“单一产品版本 + 包格式版本”。
6. 修复版本插件：读取失败必须使构建失败，不能静默回退到 `0.0.0`。
7. 增加契约测试：构建产物版本 = 根 VERSION = `package.json` = Tauri 配置。

> 这些改动在 Phase 8（收尾）执行，不提前修改当前版本号。

## 4. 版本记录从 3.0.0 开始生效

- 每次发布必须有：版本号、日期、变更摘要、迁移说明、已知问题。
- 3.0.0 的 CHANGELOG 应包含：重构范围、主题系统、包格式、取消模块、归档说明、数据迁移边界。
- 主题包与功能包使用独立版本；`apiVersion` 与应用版本解耦。

## 5. 桌面优先与多端架构准备

- 本轮重构只交付桌面端（Windows 优先，macOS/Linux 构建链保留）。
- 现有 Android/iOS 代码不进入重构范围；在 3.0.0 前冻结，后续再决定迁移或归档。
- 用户于 2026-11-10 补充：产品远期需要多端适配，从当前即考虑可扩展性。当前明确业务规则、应用服务、存储与平台能力的边界，具体提案见 [13-system-architecture.md](13-system-architecture.md)。
- 业务语义与资源契约跨端一致，界面动线与导航按设备特点设计；首期先完成桌面交互与公共组件基础。
- 多语言、主题和字体等通过可扩展的登记与加载机制管理，默认资源也使用共同契约。
- 其他技术栈迁移在桌面端稳定后再评估。

## 6. 与包系统的关系

- 3.0.0 是应用版本；主题/资源/数据/功能包各有独立版本。
- 数据包 `d3el` 需要记录导出时的应用版本与 schema 版本，用于兼容迁移。
- 主题包的主题 API 从 `apiVersion: 1` 开始，不随应用大版本自动跳跃。

## 7. 待确认

- 根 VERSION 与现有模块 VERSION 是否在 3.0.0 前就并存（建议并存到切换日）；
- Python sidecar 是否保留独立版本号（建议保留内部版本，但不对外发布）；
- macOS/Linux 是否算 3.0.0 的交付范围（建议仅保留构建能力，不宣称验收）；
- 3.0.0 是否需要单独的迁移工具或仅支持全新安装/导入。
