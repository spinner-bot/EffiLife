## 1. 协作方式与阅读说明

用户提供产品初衷、核心关系和关键取舍，Codex 据此撰写完整草案，自行拟定常规交互和技术细节。用户通过审计草案修正方案。提问集中在影响产品方向、无法从已有要求合理判断的问题上。

本文使用两类编号：

- **R：用户已明确的要求**。保留原意，作为后续方案的依据。
- **P：Codex 提案**。为形成可审阅的完整方案而拟定，供用户修改；列出提案不代表用户已经批准。

字段布局、默认值、按钮位置、录入时间格式等细节由 Codex 先拟，随具体页面设计补充。当前审计首先关注产品关系、内容层级与使用动线。

## 2. 设计初衷与产品定位

**R-001 起点与远期方向。** EffiLife 起源于作者未被现成软件满足的实际需求，并考虑长期产品化与商业化。当前先讨论产品本身。

**R-002 持续生活管理。** 产品面向个人持续、全方位的生活管理。其复合模型旨在适配现代人快节奏、多任务的城市生活，覆盖工作、生活和休息等方面。

**R-003 时间与事件两条主线。** 核心是将时间和事件合理关联。两条主线分别组织时间分配与事务推进，并能共同表达用户的实际行动。关联需要减少重复操作，同时保留两种视角的管理价值。

**R-004 零散待办的补充职责。** 待办管理订票、取快递、买盐等事项，保留其独立使用场景和既有优先排位算法。

**R-005 并行计划。** 用户可以同时推进多份主题明确的计划，借助时间视角了解每天的投入和生活分配，并处理日常待办。

**R-006 事件侧基本单元。** 一份 `Plan` 是围绕明确主题组织的整份计划，包含基本信息、计划内容和执行日志。保留条目定位、分组及近似树状层级的组织价值。

**R-007 进展日志。** `log` 是核心特色，支持记录具体子项取得进展但尚未完成的情况。一次推进与最终完成具有不同含义。

## 3. 统一录入方向

### 3.1 用户提出的要求与探索方向

**R-008 减少重复记录。** 用户不应每做一件事，都先进入时间侧记用时，再进入事件侧登记进展。

**R-009 统一入口。** 用户希望日常行动采用统一、醒目的录入入口，同时承接已纳入计划的行动和吃饭等未纳入计划的生活事件。

**R-010 类别关联方向。** 用户提出一种可能方案：为计划条目指定时间侧类别，并支持从任意父节点统一指定下方子条目的类别，记录时自动归类。这是待细化的设计方向，具体继承、覆盖与存储规则由草案提出。

### 3.2 录入方案提案

**P-001 以本次行动组织录入。** 设置全局“记录”主入口。用户填写本次做了什么及实际用时，可关联计划子项并记录进展；确认提交后，由软件维护两个视角的对应信息。

| 情境 | 时间侧表达 | 事件侧表达 |
|---|---|---|
| 推进某个计划子项，尚未完成 | 本次实际时间及类别 | 关联子项的进展日志，保留未完成状态 |
| 完成某个计划子项 | 本次实际时间及类别 | 记录完成状态；日志展示方式随页面草案细化 |
| 吃饭等独立生活事件 | 本次实际时间及类别 | 可独立记录，无需先创建主题计划 |

该表描述一次行动同时具有时间与事件信息时的处理。原有历史进展日志可以保留其内容和发生时刻，实际用时缺失时明确表示未知。

**P-002 自动带出已有信息。** 选择计划条目后带出其名称、所属计划和时间类别，允许调整本次记录。统一入口保持同一套录入逻辑，并可使用当前页面已选中的条目作为初始上下文。

**P-003 父节点提供批量类别设置。** 父节点展示操作范围；下方尚未指定类别的条目默认采用该类别，已有明确类别的条目保留原值，并提供显式覆盖选项。新增条目的默认类别采用最近上级指定值。具体规则待页面草案与数据方案共同审计。

**P-004 时间填写采用事后补录作为默认方案。** 草案支持实际起止时间与时长之间的便捷填写，允许调整结束时间。计时操作与字段排列后续拟定，用户无需在当前阶段逐项选择。

## 4. 内容层级与使用动线

**R-011 为“看”专门设计。** 查看状态、浏览进展和理解信息本身就是完整的使用目的，需要专门的组件与界面。

**R-012 降低路径负担。** 高频操作应容易到达，减少进入三四层菜单、反复切换和复杂重复操作。内容层级、信息展示和交互共同组成使用动线。

### 4.1 一级结构提案

**P-005 采用一套主导航与全局记录入口。** 桌面主导航初拟如下，名称、顺序与布局均可在审计中调整。

| 入口 | 主要职责 | 第一层应提供的内容 |
|---|---|---|
| 总览 | 了解当前生活与事务状态 | 今日时间分配、并行计划进展、需要处理的待办、最近行动 |
| 计划 | 组织并持续推进主题事务 | 并行计划、主题结构、具体子项、执行日志 |
| 时间 | 了解和安排时间投入 | 日期切换、当日分配与记录、历史时间信息 |
| 待办 | 收集与处理零散事项 | 待办清单、优先排位、临近截止事项、分类筛选 |
| 设置 | 管理产品行为与个性化配置 | 按用户目的组织的设置分区、主题与包管理、数据管理 |

记录主入口在各主页面保持稳定位置；相关内容页通过明确的对象链接衔接。计划和待办分别可直接进入，时间侧与事件侧通过共同记录和上下文链接关联。

日报、周报等专门回顾能力见远期目标。当前的总览与时间历史继续承接已有基础信息展示。

### 4.2 主要动线提案

**P-006 围绕使用目的安排路径。**

| 使用目的 | 拟定路径 | 路径需要保留的信息 |
|---|---|---|
| 看目前的生活状态 | 打开总览即可查看主要信息，按需进入具体视角 | 当前日期与展示范围 |
| 看某项重要事务推进情况 | 总览中的计划摘要 → 该计划的结构与日志 | 计划身份、选中条目与最近进展 |
| 记录一次行动 | 全局记录入口 → 填写并提交 → 返回原场景 | 输入草稿、关联条目、原页面位置 |
| 从时间记录理解投入去向 | 时间记录 → 关联计划条目及其进展 | 原记录与时间范围 |
| 从计划理解已有投入 | 计划条目 → 关联执行日志与实际时间记录 | 条目身份及相关历史 |
| 处理零散事项 | 待办入口 → 收集、查看排位或处理事项 | 分类、筛选和清单位置 |

操作完成后更新对应视角，保留用户原来的浏览上下文。常用动作直接在相关内容附近呈现，较少使用的管理操作逐步展开。

### 4.3 为浏览设计的组件提案

**P-007 建立可独立阅读的信息组件。** 优先设计每日时间分配、并行计划摘要、条目进展、执行日志流、待办摘要等组件。组件显示清楚的对象、时间范围、状态和必要说明，再提供进入详情或相关操作的位置。

总览各区呈现核心信息与变化，并能进入对应视角；编辑控件在用户开始相关操作后展开。日志内容保留进展描述，时间信息同时区分发生时刻与实际用时。

## 5. 视觉与交互方向

**R-013 现代、清爽、美观。** 界面需要达到成熟个人产品的品质，将信息展示与交互体验共同设计，支持长期舒适使用。用户明确反对旧界面类似简陋开发工具设置面板的体验。

**P-008 默认视觉采用轻量桌面工作台方向。** 使用中性色表面、清楚的文字层级、适度的信息密度、稳定的分区与克制的强调色。通过分栏、列表和上下文详情利用桌面空间；交互动作就近出现。字号、间距、颜色与控件状态由统一体系管理。

字体沿用已决定的 Inter Variable 与 Noto Sans SC 子集；组件底层沿用 Reka UI。具体色值、布局尺寸和动效由 Codex 在设计地基与页面草案中提出。

**P-009 先确定一套完整的默认界面。** 以总览为试点，将浏览状态、主要操作与进入详情的路径一起展示，审计后推广到其他页面。旧 25 套主题按已有决策保留，并通过后续主题运行时与迁移方案承接。

## 6. 连续使用与数据关联提案

**P-010 一次提交具有完整结果。** 一次行动涉及时间记录与计划信息时，保存结果明确反映整个操作。失败保留草稿；出现部分写入时，由软件维护可恢复的操作状态，重试应避免产生重复记录。具体事务或补偿机制由数据与实现方案决定。

**P-011 历史关联可追溯。** 行动、日志、条目与时间记录之间使用稳定引用。修改实际用时后，对应统计更新；修改进展描述后，对应日志展示更新。删除或解除关联的影响需要向用户说明，并在数据方案中定义恢复规则。

**P-012 连续积累覆盖跨日使用。** 页面支持查看历史日期，保留多次推进同一条目的过程；跨日的记录按实际日期与时间表达。累计实际投入、计划预计用时和条目完成状态分别表达。

本文定义产品行为与数据关系的要求。数据 schema、存储位置及与现有协议的迁移方案在后续技术文档中具体设计。

### 6.1 多端与系统级可扩展性

**R-014 从开始考虑多端。** 产品远期需要多端适配，当前即应在系统架构中考虑可扩展性。首期交付以桌面端为主，架构需要明确平台能力与业务规则的边界。

**R-015 资源与能力可扩展。** 多语言、主题、字体等系统需要支持后续新增和替换，避免初期把固定选项和具体实现散布到各处。用户要求采用模块化思维与系统级架构设计。

**P-013 通过共同契约与适配器组织系统。** 领域规则、应用服务、平台与存储适配、展示交互、资源与扩展系统分别承担明确职责；不同端遵循一致的记录与关联语义，采用适合设备的界面动线。

**P-014 语言、主题与字体通过登记和加载机制扩展。** 界面从注册目录生成选项，资源通过稳定标识与语义角色引用，加载、切换和失败回退由对应服务统一管理。已有字体决定作为默认资源，后续新增字体走同一机制。

完整职责划分与扩展验收提案见 [13-system-architecture.md](13-system-architecture.md)。

## 7. 验收场景提案

以下场景用于后续页面与实现审计，不表示当前代码已经具备这些行为：

1. 用户打开总览，直接了解当天时间分配、多个主题计划进展与待办情况。
2. 用户为一个尚未完成的计划子项记录实际投入与进展，只需提交一次；时间侧与日志侧都能看到相应信息。
3. 用户记录吃饭等生活事件，可以直接完成录入。
4. 用户通过父节点为下方条目统一设置时间类别，并能理解已有类别的处理范围。
5. 用户从某条时间记录进入关联计划，能定位到对应条目与进展；返回后保留原来的浏览位置。
6. 保存失败时，用户保有已填写内容和清楚的恢复操作，重试成功后没有重复记录。
7. 用户仅浏览时，能够完整理解概览、分配和进展，无需进入编辑流程。
8. 新增语言、主题或字体时，通过资源与登记机制接入；核心页面和业务流程继续使用共同契约。

现有七档视口、WCAG AA、视觉回归和主题切换质量门槛继续作为重构依据，具体见 [02-refactor-process.md](02-refactor-process.md)。

## 8. 后续审计与远期目标

本稿首先供用户审计以下三处：

1. 产品定位与时间、事件、待办的关系是否准确；
2. 总览、主导航与统一录入是否形成合理的日常使用路径；
3. 默认视觉方向是否符合长期使用的预期。

用户可以按 R/P 编号修改。Codex 根据反馈完善页面方案，主动检查跨章节影响，常规细节先形成具体提案。

产品化与商业化、日报/周报、智能穿戴、小型 AI agent、语音输入与后续多端交付统一记录于 [12-long-term-goals.md](12-long-term-goals.md)。
